# 分诊（Triage）

推动项目 issue 跟踪器上的 issue 流经一个由分诊（triage）角色构成的小型状态机。

如果本仓库把外部 pull request 也视作一类请求来源（见 issue 跟踪器配置），分诊同样覆盖它们：**PR 就是附带代码的 issue**——相同的角色、相同的状态、相同的状态机，只是下文标注「for a PR」处有少量差异。按跟踪器配置把一个裸 `#42` 解析为 issue 或 PR。

分诊期间发往 issue 跟踪器的每一条评论或 issue **都必须**以这条免责声明开头：

```
> *This was generated by AI during triage.*
```

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何撰写经久耐用的代理简报

## 角色

两个**类别（category）**角色：

- `bug` — 某处出了问题
- `enhancement` — 新功能或改进

五个**状态（state）**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者补充更多信息
- `ready-for-agent` — 已完整说明，可交给 AFK 代理
- `ready-for-human` — 需要人工实现
- `wontfix` — 不会处理

对于 PR，同样这些状态是针对所附代码来理解的：`ready-for-agent` 表示已附上简报，代理应对该 diff 推进下一步；`ready-for-human` 表示它已就绪、可由人工合并。

每个经过分诊的 issue 都应恰好带一个类别角色和一个状态角色。如果状态角色彼此冲突，先标记出来并询问维护者，再做任何其他事。

这些是规范化的角色名——issue 跟踪器中实际使用的标签字符串可能有所不同。映射关系应当已经提供给你了——如果没有，运行 `/setup-matt-pocock-skills`。

状态转移：未打标签的 issue 通常先进入 `needs-triage`；从那里再转入 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 就回到 `needs-triage`。维护者可以随时覆盖——把看起来异常的转移标记出来，并在继续前询问。

## 调用

维护者调用 `/triage`，用自然语言描述他们想要什么。理解请求并据此行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的内容

查询 issue 跟踪器，按从旧到新呈现三个分组：

1. **Unlabeled** — 从未分诊过。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且自上次分诊记录以来有报告者活动** — 需要重新评估。

当 PR 在范围内时，把外部 PR 也纳入这些分组，并给每一行打上 `[PR]` 或 `[issue]` 标记。发现（discovery）只浮现*外部* PR（跟踪器配置定义谁算外部）——协作者尚在进行中的 PR 不属于分诊工作。这个过滤仅用于发现；被显式点名的 PR 无论作者是谁都始终会被分诊。

显示计数，并为每个条目给出一行摘要。让维护者来挑选。

## 分诊指定的 issue 或 PR

1. **Gather context.** 读完整个 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要读 diff）。解析任何既有的分诊记录，这样你就不会重复追问已解决的问题。用项目的领域术语表探索代码库，并尊重该领域内的 ADR。针对代码库跑两项检查：(a) **redundancy** — 按领域概念（而不只是请求的措辞）搜索所请求行为是否已有实现，并报告你查过哪里。如果找到，它就是一个已实现的 `wontfix`（第 5 步）。(b) **prior rejection** — 读 `.out-of-scope/*.md`，并浮现任何与本请求相似的记录。

2. **Recommend.** 把你对类别和状态的推荐连同理由告诉维护者，再附上一段与该请求相关的简短代码库摘要——包括它是否已被实现。等待指示。

3. **Verify the claim.** 在任何盘问之前，先确认该主张站得住脚。对 bug，按报告者的步骤复现。对 PR，确认 diff 确实做到了它所声称的——把它 check out 下来，跑相关的测试或命令。报告发生了什么：已确认（附代码路径）、失败，或细节不足（这是一个强烈的 `needs-info` 信号）。一次已确认的验证会让代理简报有力得多。

4. **Grill (if needed).** 如果请求需要进一步充实，把 `/grilling` 和 `/domain-modeling` 技能一起运行起来——一次一个问题地把它盘问成型，打磨领域术语，并随着决策落定就地更新 `CONTEXT.md`/ADR。

5. **Apply the outcome:**
   - `ready-for-agent` — 发一条代理简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 结构与代理简报相同，但注明为什么它不能被委派（需要判断取舍、外部访问、设计决策、手动测试）。
   - `needs-info` — 发分诊记录（模板见下文）。
   - `wontfix` — 关闭，评论内容取决于*为什么*：
     - **Already implemented** — 该改动已存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（那个知识库针对的是*被拒绝*的请求，而非已构建的）。
     - **Rejected (bug)** — 礼貌地解释，然后关闭。
     - **Rejected (enhancement)** — 写入 `.out-of-scope/`，从评论中链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用该角色。如果有部分进展，可选地加一条评论。

## 快速状态覆盖

如果维护者说 "move #42 to ready-for-agent"，就相信他们并直接应用该角色。确认你即将做的事（角色变更、评论、关闭），然后行动。跳过盘问。如果未经盘问会话就移动到 `ready-for-agent`，询问他们是否想写一份代理简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把盘问期间解决的所有内容都记到 "established so far" 之下，免得这些成果丢失。问题必须具体、可执行，而不是 "please provide more info"。

## 恢复先前的会话

如果 issue 或 PR 上存在既有的分诊记录，读它们，检查报告者是否回答了任何尚未解决的问题，并在继续之前呈现一幅更新后的全貌。不要重复追问已解决的问题。
